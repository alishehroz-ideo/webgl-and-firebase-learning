04 Asset loading & caching

Download once. Reuse forever.

Art lives in the cloud and loads on-demand — only when a sticker or background is first shown. Then it’s kept in two tiers so it never downloads twice.

1 Memory

In-session Dictionary — instant. Gone when the tab closes.

2 Disk

Browser IndexedDB (via persistentDataPath) — survives reloads.

3 Download

Miss both → fetch from Firebase Hosting once, store in both tiers.

Fridge
The cache (browser)
what you’re using now · limited · old items evicted
Warehouse
Cloud + CDN
has everything · always restockable

WebGL limits (named honestly): IndexedDB is per-browser, has a quota, and can be evicted; there are no background threads; big textures hit a memory ceiling — so a cache miss just re-downloads. Plus in-flight de-dupe: the same image requested twice shares one download.

05 Key decisions & challenges

Where the real engineering was.

Decision

REST, not the SDK

The Firebase Unity SDK doesn’t support WebGL. Everything talks to Firebase over its REST API with UnityWebRequest — the WebGL-safe path.

Decision

References, not images

Books store asset IDs + normalized transforms. The recipe stays tiny; heavy art is hosted once and cached. Art can be swapped with zero code changes.

Challenge

The WebGL gzip fight

Firebase strips Content-Encoding from .js and caches encodings inconsistently — the game wouldn’t load. Fix: ship the payload uncompressed and let Firebase gzip it natively.

Decision

Free-tier by design

Runs entirely on Firebase’s free plan — Realtime DB + Hosting, covers stored inline, no Cloud Functions, no card.
