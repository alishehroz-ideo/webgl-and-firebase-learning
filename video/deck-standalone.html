01 Overview of the implementation

Three screens. One simple loop.

Everything a child does is make a book, save it, then read it back — across just three screens.

Under the hood: a Unity app exported to WebGL (runs in the browser), with all art and saved books living on Firebase — reached over plain web requests (REST), no server of my own.

03 How a book is saved & loaded

Save the recipe, not the picture.

A saved book is tiny — it just lists which sticker and where, never the image itself. Positions are stored as percentages, so it looks right on any screen.

05 The tricky parts I solved

Where the real engineering was.

Talking to Firebase the hard way

Firebase's usual shortcut doesn't work in the browser — so I talk to it directly over the web, and make each request wait smoothly without ever freezing the screen.

REST · UnityWebRequest wrapped in a TaskCompletionSource → async/await

A sticker that stays put on any screen

A pixel position means nothing across different screens. I store each position as a percentage (0–1) — so a book made on a phone looks perfect on a desktop.

pointer → stage-local → normalized 0–1 · RectTransformUtility

Remembering images with no hard drive

The browser has no real disk. So I keep images in memory and the browser's own storage — and if the same image is asked for twice at once, both share one download.

IndexedDB via persistentDataPath · in-flight de-duplication

Getting it to boot online

The host was mangling the compressed game files, so the app wouldn't start. The fix: ship the files uncompressed and let the host compress them instead.

Firebase strips Content-Encoding on .js → serve raw, Firebase gzips natively
