04 Asset loading & caching

Download once. Reuse forever.

Art lives in the cloud and loads on-demand — only when a sticker or background is first shown. Then it’s kept in two tiers so it never downloads twice.

1 Memory

In-session Dictionary — instant. Gone when the tab closes.

2 Disk

Browser IndexedDB (via persistentDataPath) — survives reloads.

3 Download

Miss both → fetch from Firebase Hosting once, store in both tiers.

Fridge
The cache (browser)

Warehouse
Cloud + CDN
has everything · always restockable

WebGL limits (named honestly): IndexedDB is per-browser, has a quota, and can be evicted; there are no background threads; big textures hit a memory ceiling — so a cache miss just re-downloads. Plus in-flight de-dupe: the same image requested twice shares one download.

05 Key decisions & challenges

Where the hard engineering was.

Challenge

Async REST in a single-threaded runtime

The Firebase Unity SDK can’t run in WebGL — so the whole data layer talks to Firebase over REST. Unity’s requests are callback-based, so I wrap each one in a TaskCompletionSource for clean async / await — no coroutines, never blocking the frame.

Challenge

Resolution-independent placement

A dragged sticker’s pixel position is meaningless across screens. I map pointer → stage-local with RectTransformUtility, then to normalized 0–1 coordinates — so a book made on a phone replays pixel-perfect on a desktop.

Challenge

A cache with no filesystem

WebGL has no disk. The cache keeps sprites in memory and mirrors bytes to the browser’s IndexedDB via persistentDataPath — with in-flight de-duplication, so two requests for one asset share a single download.

Challenge

Booting a compressed build on a static host

Firebase strips Content-Encoding from .js and caches encodings inconsistently — the WebAssembly refused to load. Fix: ship the payload uncompressed and let Firebase gzip it natively.
